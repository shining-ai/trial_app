# レビューのための説明: 動画の結合機能

ブランチ `feature/video-merge`(分岐元 `main` の `4e1955c`)。17コミット、141ファイル(package-lock.json を除く)。本体のコード(`backend/app`・`frontend/src`)は67ファイル・約2,000行で、残りはテスト・E2E・プラン・記録。push はしていない。

判定はせず、確かめてほしい点と判断の材料だけを書く。経緯の詳細は [video-merge.log.md](video-merge.log.md)、プランからの変更は [video-merge.md](video-merge.md) の「実装で追加・変更した点」(I1〜I30)にある。

## 1. 何ができるようになったか

- 複数の動画をアップロードし(1本4GB・4Kまで、100本まで)、ボタン(上へ・下へ・先頭へ・末尾へ・削除)で並べ替え、合計30分以内なら結合して MP4 をダウンロードできる
- 解像度・形式・フレームレート・音声の有無が違う動画も、拡大せず中央に置いて縁を黒で埋め、最も高い fps と 48kHz・ステレオの音声にそろえて結合する
- 結合はジョブとして動き、画面に進み具合が出る。同時に実行できる結合は1件

## 2. 動かし方

```
docker compose up --build        # http://localhost:5173
docker compose run --rm --build backend pytest
docker compose run --rm --build frontend npx vitest run
docker compose run --rm --build e2e
docker compose --profile e2e down
```

最後に実行した結果: backend 206件・frontend 148件・E2E 6件、すべて通過。

## 4. 人間の判断が必要な点

レビューの3ラウンドで決めきれず、記録して残したもの。

1. **`-xerror` の副作用**(I16): 途中で切れた動画が「短い出力のまま成功」にならないよう、1段目に付けた。一方で、軽いデコードエラーを含む正しい動画まで結合で失敗させるおそれがある。先頭が欠けた MPEG-TS では問題なく変換できることを確かめたが、ほかの種類の動画では確かめていない。代わりに「1段目の出力の長さを期待値と比べる」方式もある
2. **`-t` による切り詰め**(R2): 申告された長さのすり抜けを防ぐため、1段目の出力をメタ情報の長さで打ち切っている。ffprobe が長さを短く見積もる動画(古い FLV など)では、黙って短くなる。1 と同じく、出力の長さを確かめる方式なら両立できる
3. **アップロード時の空き容量の確認(507)**(I19): プランでは「入れない」(R8)と決めていたが、セキュリティのレビューを受けて入れた。要件はアップロード時の507を禁じていないため、要件とは矛盾しないと判断した。`Content-Length` のない送信や同時アップロードには効かない
4. **ポートの公開範囲**: `compose.yaml` の `8000:8000`・`5173:5173` は全インターフェースで待ち受ける。認証がないため、同じ LAN の端末からアップロード・削除・ダウンロードができる(今回の差分の外の既存の行)。ローカル専用なら `127.0.0.1:` を付ける案がある
5. **想定内の拒否も error で記録する**: 動画でない・解像度超過の422も error のログに出している。logging.md ルール3 に沿った判断だが、ログが多くなる
6. **入れ物の形式の許可リスト**: MP4・MOV、MKV・WebM、AVI、MPEG-TS・PS、WMV、FLV。これ以外の形式は、動画でも「動画として読み込めませんでした」になる(以前の確認で回答をもらっていない)

## 5. 手動で確かめてほしいこと

自動テストは、FFmpeg で作った数秒の単色の動画で確かめている。次は確かめていない。

- 実際のスマホの縦動画(回転情報付き、HEVC、可変フレームレート)と4K動画で、アップロードから結合・ダウンロードまでを1回通す(プラン3のタスク6)。処理時間と画面の表示崩れも見る
- 4K の横長と縦長を混ぜたとき(出力 3840x3840)の処理時間
- 空き容量が足りないときに、ブラウザで「保存先の空き容量が足りません」が出るか(受信前に接続を閉じるため、通信エラーに見えるおそれがあるとの指摘あり。未実測)

なお、Vite の転送で4GBの本文が流れることは、curl で確かめた(4GBちょうどは最後まで受け取られ、4GB+1バイトは受信前または受信中に413)。

## 6. プランから変えた主な点

I1〜I30 の全体は [video-merge.md](video-merge.md) にある。影響の大きいもの:

- ジョブの状態を `lib/` ではなく merge 機能に置き、download はジョブの状態を参照せず結果ファイルの有無で判断する(R5)
- メタ情報にストリームの絶対番号を持たせ、カバー画像を映像として使わない(I14)
- 回転は表示行列からだけ読み、タグの `rotate` は使わない(I25)
- 30分の判定は、各動画の長さをミリ秒の整数にしてから足し、画面とサーバーで同じ計算にする(I24)
- 「削除」を押した時点で一覧から外し、失敗したら戻す(I30)

## 7. 残っている既知の指摘(P2・未対応)

理由は記録にある。主なもの:

- 子プロセスの出力の大きさに上限がない(巨大なタグで60秒まで CPU を使う)
- 成功の直前に後片付けが失敗すると、完成した結果も消して失敗にする
- 壊れたメタ情報・ダウンロード直前のファイルの消失で500になる
- 設定値(`STALE_FILE_HOURS`、`MAX_FPS` など)の範囲を確かめていない
- コーデックの許可リスト、`POST /api/merges` の本文の大きさ、ファイル名の制御文字の制限がない

## 8. 進め方で記録しておくこと

- テストはモジュールごとに先に書き、Red を確かめてから実装した(tdd スキルの「1件ずつ」ではなくモジュールごと)。E2E と、後から足したテストは実装が先にあったため最初から通り、実装をわざと壊して失敗することを確かめた。1件(URL を参照する再生リスト)は、許可リストを外しても FFmpeg 自体が拒否するため通る
- プランで Haiku・Sonnet に割り当てた backend・E2E のタスクも、整合を保つためメイン(Opus)で行った。frontend は Sonnet のサブエージェントに任せた
- プランにない変更の多くは、プランへの追記が実装の後になった
- ラウンド3で直した2件(I29・I30)は、再レビューを受けていない
