# architecture

## 構造(どこに何を置くか)

- `backend/app/features/<機能名>/` — バックエンドの機能ごとのコード(upload、merge、download)
- `backend/app/lib/` — 機能横断の共通処理のみ
- `frontend/src/features/<機能名>/` — フロントエンドの機能ごとのコード
- `frontend/src/lib/` — 機能横断の共通処理のみ

置き場所に迷ったら、この順で問う。

1. 特定の機能だけが使う処理 → その機能の `features/<機能名>/`
2. どの機能にも属さない基盤 → `lib/`
3. 複数の機能で使いたい処理 → すぐに共通化せず、まず各機能に置く

## 1ファイル1責務

- ファイルの担当を一文で言えること。「並び順からFFmpegの引数を組み立てる」は合格、「結合まわりの処理いろいろ」は失格
- ファイルが肥大したら、責務の境界で分ける

## 機能境界

- `router.py` に処理の本体を書かない。同じ機能フォルダの関数を呼ぶだけにする
- 保存先のパスを各機能で組み立てない。`lib/disk_storage.py` を経由する
- FFmpegやffprobeを各機能から直接起動しない。`lib/run_process.py` を経由する
- `index.ts` や `__init__.py` に集約して再エクスポートしない。実ファイルから直接importする

## 副作用の分離

- 判断、計算、変換は純粋関数に集める(例: `build_concat_args.py`、`moveItem.ts`)
- ファイルの読み書き、子プロセスの実行、環境変数の参照は外側の薄い層に寄せる
- 狙いは、複雑なロジックを外部依存なしでテストできる形に保つこと
